# 1. Foundations of Generative AI and Prompting

## The mental model

Think of an LLM as an extraordinarily well-read autocomplete engine with a flexible working memory. It does not retrieve a guaranteed fact from a filing cabinet. It predicts what sequence of tokens is likely to follow the context it has been given.

That distinction explains both the magic and the risk: the model can produce a beautiful explanation, but fluency is not proof of truth.

A prompt is best understood as an **interface contract** between your application and the model. Like an API contract, it should define the job, available data, rules, output shape, and what to do when the request cannot be completed.

```text
quality = f(model, instructions, context, examples, parameters, tools, evaluator)
```

- **Model:** The model's capabilities, knowledge, limitations, and behavior.
- **Instructions:** The task, rules, constraints, and success criteria given to the model.
- **Context:** The relevant information supplied to help the model complete the task.
- **Examples:** Demonstrations that show the model the desired reasoning pattern or output format.
- **Parameters:** Generation controls such as temperature, top-p, maximum tokens, and stop sequences.
- **Tools:** External capabilities that let the model retrieve information or take authorized actions.
- **Evaluator:** The tests, metrics, or human review used to measure whether the result is good enough.

Improving only the wording is like trying to fix a restaurant by rewriting the menu while ignoring the kitchen, ingredients, and quality checks.

## What an LLM does

Text is converted into tokens, tokens into numerical representations, and those representations are processed through transformer layers. Attention allows the model to compare parts of the context and estimate relationships. The model then produces a probability distribution for the next token and repeats the process.

Useful consequences:

- Tokens are pieces of text, not always complete words.
- The context window is shared by instructions, documents, history, tool results, and output.
- Generation is probabilistic, so identical requests may differ.
- Training knowledge may be incomplete, stale, or wrong.
- The model can follow a pattern without understanding it as a human does.

### Analogy: a talented improviser

Imagine an improviser who has read millions of books. Give them a clear scene and they can continue it convincingly. Give them contradictory stage directions, missing facts, and a demand for certainty, and they may improvise a plausible answer. Your prompt is the stage direction; your application must still check the performance.

## Model controls

- **Temperature:** how much variation is allowed when sampling. Lower values usually improve repeatability, not truth.
- **Top-p:** restricts sampling to a cumulative probability mass.
- **Maximum output tokens:** caps the response and can cause truncation.
- **Stop sequences:** tell generation where to stop.
- **Structured output:** constrains responses to a schema when supported.
- **Tool calling:** allows the model to request an external action; your code must authorize and validate it.

Choose controls by task:

| Task | Typical preference | What to measure |
|---|---|---|
| Classification/extraction | Low variation, schema | Validity and accuracy |
| Summarization | Low to medium variation | Coverage and faithfulness |
| Brainstorming | Medium to high variation | Diversity and usefulness |
| Code generation | Low to medium variation | Tests, security, compilation |
| Image/video creation | More variation plus controls | Composition and consistency |

## The anatomy of a reliable prompt

```text
Task:
Classify the customer message into exactly one category.

Context:
<customer_message>
{{message}}
</customer_message>

Rules:
- Use the customer's primary issue.
- Do not infer sensitive attributes.
- If ambiguous, choose other.

Output:
Return JSON matching:
{
  "category": "billing | access | bug | feature_request | other",
  "confidence": 0.0,
  "reason": "short evidence-based explanation"
}
```

Read this like a contract:

- Task is the function name.
- Context is the input object.
- Rules are invariants(conditions that must always remain true).
- Output is the return type.
- The evaluator is the test suite.

## Common beginner mistakes

1. **Vague objective:** “Tell me about this.” Define audience, scope, and desired decision.
2. **No failure behavior:** Tell the model when to abstain, ask a question, or return null.
3. **Mixed trust levels:** Separate instructions from user text and documents.
4. **Overlong prompts:** Remove instructions that do not affect an observed failure.
5. **Trusting confidence:** A confidence number generated by the model is not calibrated automatically.
6. **Skipping application validation:** Parse JSON, check ranges, and authorize tools in code.

## Practice lab

Run one classification prompt over 20 inputs with two parameter(temperature, top_p) configurations. Record:

- Valid JSON rate
- Correct label rate
- Average latency
- Input and output tokens
- Variation across repeated runs
- Cases where the model should have abstained

Change one variable at a time. The goal is to learn which part of the system caused the difference.

## Takeaway

The foundational question is not “What clever phrase makes the model behave?” It is “What contract, context, controls, and checks make this behavior reliable?”
